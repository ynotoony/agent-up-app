# 领域上下文

本文件只描述业务含义，不描述技术实现。词汇格式遵循 domain-modeling 的 CONTEXT-FORMAT：加粗术语 + 1～2 句定义（描述它是什么，不是它做什么）+ `_Avoid:_` 近义词；只收本项目特有概念，通用编程概念不进。只登记用户明确给出或从可靠来源核验过的词汇；没有依据的写 `【待定：…】`，不编造业务事实。

## 角色

**用户**：提出需求、评论、做关键决定、暂停或继续任务、反馈和接受结果。_Avoid:_ 直接编辑事实文件。

**主 Agent**：理解需求、质疑范围、拆分任务、整合结果并向用户汇报；在 C0/C1 低风险范围内可以直接实施。_Avoid:_ 自己审查自己的实现。

**执行 Agent**：按已确认范围实施任务。_Avoid:_ 主 Agent、审查 Agent。

**审查 Agent**：独立检查实施结果；高风险任务不得与执行 Agent 相同。_Avoid:_ 自审。

## 核心对象

**项目事实**：保存在项目根目录 `.agentup/` 中、可被 App 和 Agent 共同读取的唯一事实。

**讨论**：用户、Agent 和系统围绕当前需求产生的消息、决定、范围变化、检查和结果事件。

**任务范围**：当前任务涉及的文件集合，以及每个文件被纳入的原因和版本。

**结果版本**：一次可追溯、不可覆盖的交付结果及其验收状态。

## 状态

**需求生命周期**：需求从提出、讨论、执行到验收的用户可见生命周期；当前批准的状态和值域与转换见 [`SPEC-001`](./specs/001-m0-foundation.md)，本文件不重复维护状态机。

Review 失败禁止 Commit；用户接受不能由系统自动推断。

## 流程

选择项目 → 输入一句话需求 → 讨论 → Agent 生成方案和任务范围 → 用户决定 → 执行 → Review → 修正或形成结果 → 用户反馈 → 新一轮修改 → 接受结果。

## 范围边界

首版不做账号、团队协作、远程同步、移动端、邮件通知、多根目录、跨项目写入、应用关闭后继续执行和自动导入旧历史。
