# AgentUp 开发计划

状态：待确认
版本：v1
依据：AgentUp 产品规格说明书 v1.0、`properties/react` 交互原型、`properties/react/docs/design-system.md`

## 0. 开发目标

从空的 Tauri 2 应用开始，建立一个以项目 `.agentup/` 为事实来源、以讨论为主要交互、由 Agent 自动推进任务的本地应用。`properties/react` 只提供交互、文案、场景和视觉参考，不作为生产代码基础。

开发完成后，用户可以：

1. 添加一个项目并完成只读扫描和初始化确认。
2. 用一句话提出需求。
3. 在讨论中补充文字和图片。
4. 查看 Agent 当前理解、方案和动态任务范围。
5. 在关键取舍上做决定。
6. 查看自动拆分、指派、执行、Review 和修正过程。
7. 打开结果、反馈问题、创建下一轮修改并接受结果。
8. 关闭应用后从项目事实恢复当前状态。

## 1. 范围与约束

### 1.1 从原型继承的产品事实

- 当前信息架构：我的工作、项目空间、任务详情、待我决定、结果、设置。
- 统一任务详情布局：讨论主题、唯一当前动作、讨论流、任务范围和辅助信息。
- 项目内 `.agentup/` 为默认且唯一的事实保存位置，不向用户提供存储位置选择。
- 三个原型场景：界面改造、Bug 修复、模糊想法评估。
- 讨论优先、卡片精简、动态任务范围和固定视口规则。

### 1.2 实现边界

- 新 App 从空目录开始，不迁移 `properties/react/src` 的组件、样式、状态模型或 demo 数据。
- renderer 技术暂定为 React + TypeScript，但使用全新目录、全新组件和全新 domain model；如果实施前改用其他 Web UI 技术，必须更新本计划。
- `properties/react` 只读登记为 prototype reference，不作为 build、runtime 或发布输入。
- 旧 `src/views/Frame*.tsx`、截图和压缩包只作为设计参考，不进入产品运行路径。

### 1.3 不做

- 不迁移旧 Pixso 静态页面和旧数据。
- 不让用户直接编辑 `.agentup/` 或项目文件。
- 不让用户直接修改阶段、依赖、验证结果或事件记录。
- 不把 SQLite 当作项目事实的唯一来源。
- 不继续增加独立看板、流程监控台或重复的顶部入口。
- 不在开发前继续扩展视觉装饰。

### 1.4 代码所有权

- 交互参考：`properties/react/`。
- 产品实现目录：仓库根目录 `/Users/bic/Projects/agent-up/`（从空实现起步）。
- 产品实现的 Tauri runtime、renderer、schemas、tests 和 docs 均属于仓库根目录。
- 设计规范：`properties/react/docs/design-system.md`，提炼为新 App 的 UI 验收基线，不直接复制样式文件。

## 2. 总体架构

当前浏览器原型无法安全完成任意项目文件写入、SQLite 管理和本地 Agent 执行，因此真实应用采用三层：

```text
React/Vite renderer
        ↓ Tauri invoke / events
Tauri 2 Rust runtime
        ↓
项目 .agentup/ + App 私有 SQLite + Agent runners
```

### 2.1 推荐运行方式

- 保留 Vite 作为 renderer 开发和构建工具。
- 使用 Tauri 2 Rust runtime，负责文件系统、SQLite、子进程和权限边界。
- 通过严格类型化的 Tauri commands 和 event channels 暴露白名单操作，不允许 renderer 直接使用系统 API。
- 使用 Tauri capabilities 明确窗口、文件、shell 和事件权限；默认拒绝，按 command 最小授权。
- 把系统 WebView 差异纳入平台测试：macOS WKWebView、Windows WebView2、Linux WebKitGTK。
- Agent provider、文件扫描器、任务编排器和事实仓库都通过接口隔离，先实现本地可替换的 provider。

### 2.2 计划目录

```text

├── src-tauri/
│   ├── src/
│   │   ├── lib.rs           # Tauri builder、命令注册、应用生命周期
│   │   ├── commands/        # typed invoke commands
│   │   ├── facts/
│   │   ├── scope/
│   │   ├── runs/
│   │   ├── agents/
│   │   ├── permissions/
│   │   └── storage/
│   ├── capabilities/        # Tauri 最小权限声明
│   ├── tauri.conf.json
│   └── Cargo.toml
├── src/
│   ├── domain/              # 新建类型、状态机、事件、校验
│   ├── repositories/        # renderer 侧仓库接口和查询适配
│   ├── runtime/             # 新建 use-case 和 Tauri adapter
│   └── components/          # 新建页面和共享组件
├── schemas/                 # JSON Schema / fixture contract
├── tests/
│   ├── unit/
│   ├── integration/
│   └── e2e/
└── docs/
```

完成标准：renderer 不直接访问文件系统；所有真实副作用都经过 Tauri typed command，并且每个 command 都有 capability、权限、错误和事件结果。

## 3. 事实层与数据规范

### 3.1 项目事实目录

每个项目根目录使用：

```text
.agentup/
├── manifest.json
├── requests/
├── discussions/
├── plans/
├── tasks/
├── scopes/
├── runs/
├── results/
├── decisions/
├── events/
└── attachments/
```

最小创建只生成 `manifest.json`、`events/` 和首次需求需要的目录。其余目录按需创建。

### 3.2 记录通用字段

当前批准的事实 envelope、状态命名空间、revision 和原子写入规则见 [`SPEC-001`](./specs/001-m0-foundation.md)。本计划不重复字段结构，避免与 schema 和规格产生第二套定义。

### 3.3 事实类型

- `request`：原始需求及其版本。
- `discussion`：用户、Agent、系统事件组成的讨论流。
- `plan`：理解、成功标准、约束、方案和拆分结果。
- `task`：主任务、子任务、依赖、负责人和当前状态。
- `scope`：当前任务涉及的文件集合及每个文件的原因、来源和状态。
- `run`：Implement、Review、Commit、命令和验证运行。
- `decision`：问题、选项、推荐理由、用户选择和影响。
- `result`：不可变交付版本、预览、证据和验收状态。
- `attachment`：图片元数据和项目内相对路径。
- `event`：独立于事实 record envelope 的不可变追加记录，其合同见 `SPEC-001`。

### 3.4 版本规则

- 旧记录不覆盖，修改产生新 revision 或新版本。
- 结果版本和任务范围版本必须可追溯到对应 plan/run。
- 所有写入使用 revision 校验；冲突时拒绝覆盖并返回可读错误。
- SQLite 可以缓存投影，但删除后必须能从 `.agentup/` 重建。

完成标准：删除 SQLite 后，执行一次重建可以还原项目、需求、讨论、任务、范围、运行、决定和结果索引。

## 4. 项目初始化与项目管理

### 4.1 初始化流程

位置：`src-tauri/src/facts/`、`src-tauri/src/storage/`、新 App 的项目管理 UI。

流程：

```text
选择文件夹
→ 只读扫描
→ 显示项目名、类型、已有文档和 .agentup 状态
→ 预览将创建的目录
→ 用户确认
→ 最小化创建
→ 写入 manifest 和初始化事件
```

完成标准：用户未确认前，项目目录没有任何写入；扫描失败只影响当前项目；初始化后可以从 manifest 恢复项目。

### 4.2 项目删除

- 删除前显示需求、讨论、结果和附件数量。
- 备份模式导出完整 `.agentup/` 快照。
- 清空模式删除 `.agentup/`，不删除项目代码。
- 两种操作都必须二次确认并追加事件。

### 4.3 多项目

- App 私有索引保存项目列表和路径映射。
- 事实始终按项目隔离。
- 全局工作页只聚合索引，不复制事实。
- 项目路径失效时显示原因，不阻塞其他项目。

## 5. 讨论与附件

位置：`src/components/Discussion*`、`src-tauri/src/attachments/`、`src/domain/discussion.ts`。

### 5.1 讨论规则

- 用户评论不要求选择类型、优先级或任务编号。
- Agent 回复必须说明保留的理解、修改的理解、方案变化和下一步。
- 评论可以触发 Agent 重新评估，但不能直接改内部状态。
- 讨论流同时承载用户消息、Agent 消息、决定、范围变化、检查和结果事件。

### 5.2 图片规则

- 支持粘贴、拖拽、本地选择和一条评论多张图片。
- 提交前可删除、替换和预览。
- 点击缩略图打开大图；不提供箭头、框选、画笔和编号标注。
- 图片写入 `.agentup/attachments/`，讨论只保存附件 ID 和元数据。
- 限制 MIME、大小和数量；失败时在输入区域附近说明修复方式。

完成标准：三种场景都能完成“文字 + 多图评论 → Agent 回复 → 记录到讨论和事实层”的流程。

## 6. Agent 上下文与任务范围

位置：`src-tauri/src/agents/`、`src-tauri/src/scope/`、`src/components/TaskScope*`。

### 6.1 上下文优先级

```text
当前需求
→ 当前讨论共识
→ 当前有效约束
→ 当前项目事实
→ 历史记录
→ 已归档或已废弃内容
```

### 6.2 范围生命周期

- 新需求、理解中、讨论中：无关联文件，显示“等待 Agent 判断”。
- 方案阶段：生成初步范围，每个文件有纳入原因。
- 实施和检查阶段：形成当前工作集，记录文件 hash 和来源。
- 方案或用户约束变化：生成新范围版本，显示新增、移除和原因变化。
- 修改反馈重新进入讨论：旧范围保留在历史，新一轮范围重新评估。
- 用户可以查看范围，不能直接编辑事实文件。

### 6.3 范围记录

每个范围项至少包含：`path`、`purpose`、`source`、`status`、`revision`、`content_hash`、`added_by`、`removed_at`。

完成标准：用户能在任务详情中看到“当前涉及什么、为什么涉及、相对上一版变化什么”；范围变化会出现在讨论和活动记录中。

## 7. 任务、决定和 Agent 编排

### 7.1 状态机

唯一的用户可见需求生命周期是 `RequestLifecycle`，当前批准的状态、转换边界和与 `TaskState`/`Phase` 的映射见 [`docs/specs/001-m0-foundation.md`](./specs/001-m0-foundation.md)。本计划不再维护第二套状态机。用户不能直接设置状态；所有状态变化必须来自 use-case 和事件。

### 7.2 自动拆分

拆分依据：多个独立结果、跨模块、并行可能、先后依赖、专业能力差异和风险等级。

每个子任务必须和主任务同构，拥有自己的：讨论、范围、负责人、运行、检查、结果和历史。

### 7.3 Agent 角色

- 主 Agent：理解、质疑、拆分、整合和向用户汇报。
- 执行 Agent：Implement。
- 审查 Agent：Review；高风险时必须与执行 Agent 不同。
- 用户：评论、决定、暂停、继续、接受或要求修改。

完成标准：能演示普通任务的 Implement → Review → Commit，以及高风险任务的不同 Agent Implement → Review；Review 失败不能 Commit。

## 8. 运行、权限与失败恢复

位置：`src-tauri/src/agents/`、`src-tauri/src/runs/`、`src-tauri/src/permissions/`、`src-tauri/capabilities/`。

- 每次工具调用前检查任务权限、项目路径和范围。
- 命令只允许在项目目录内执行，记录命令、输入、输出、退出码和耗时。
- 文件写入必须经过统一 writer，校验 revision 和 hash。
- 暂停应取消可取消运行；取消不删除讨论、结果和事实。
- Review 失败返回修正；连续失败达到阈值后暂停并请求用户决定。
- 运行进度通过 Tauri event channel 推送给 renderer；窗口重连后从事件游标恢复。

完成标准：权限拒绝、命令失败、文件冲突、Review 失败、暂停、取消和恢复都有可追溯事件及用户可理解的下一步。

## 9. 结果、反馈与历史

位置：`src/components/Result*`、`src-tauri/src/facts/results`、`src/components/History*`。

- 界面任务提供可操作预览。
- Bug 任务提供复现前后对比和验证证据。
- 分析任务提供结论、依据、限制和建议。
- 结果版本不可变；用户反馈创建新的修改上下文。
- 支持接受、要求修改、暂不处理和拒绝记录。
- 历史展示版本、评论、失败、范围变化和决定，不自动改变当前目标。

完成标准：用户可以从结果页反馈文字或多张图片，生成新一轮讨论，并能在历史中比较旧版和新版。

## 10. 全新 App 实现

产品实现从仓库根目录现有治理骨架之外的新应用代码开始：

- 不复制原型组件、CSS、状态模型、fixture 或 localStorage 逻辑。
- 先写 domain contract、Tauri command/event contract 和页面状态表，再写 UI。
- renderer 通过 repository/use-case 调用 Tauri，不直接修改事实对象。
- 新建任务详情、决定、结果、范围、讨论和历史组件；原型只作为行为参考。
- 卡片只展示一个主题；整卡点击时保留键盘焦点和 aria 语义。
- 页面固定在视口内，讨论、看板、范围和辅助信息内部滚动。
- 1440、1024、768 三档无横向溢出。

完成标准：移除 `properties/` 原型参考目录后，仓库根目录的 Tauri App 仍可独立构建、运行、测试和恢复事实；产品没有对 `properties/react` 的运行时依赖。

## 11. 安全与数据完整性

- Tauri command 最小权限、参数 schema 校验和路径规范化。
- 禁止路径穿越、任意工作区写入和未授权命令。
- 附件和命令输出限制大小，日志避免泄露密钥。
- 不把 Agent 输出直接当作可信指令；外部内容作为数据处理。
- 写入采用临时文件、fsync/rename 或等价原子策略。
- 每个项目提供事实导出和恢复检查。

完成标准：安全测试覆盖路径穿越、权限绕过、恶意文件名、超大附件、并发写入和中断恢复。

## 12. 测试与验收

### 12.1 单元测试

- 状态机合法和非法转移。
- 事件追加和 revision 冲突。
- 任务拆分、依赖解锁和父子进度。
- 范围生成、范围差异和范围恢复。
- 决定解析和未解决决定阻塞。
- 附件校验和结果版本状态。

### 12.2 集成测试

- 项目初始化确认前无写入。
- `.agentup/` 写入后可读取和重建 SQLite。
- 运行失败、Review 失败、修正和暂停恢复。
- 多项目事实隔离。
- 删除项目备份和清空流程。

### 12.3 E2E 测试

覆盖三个场景的完整路径：

```text
输入需求 → 讨论 → 图片评论 → 范围生成 → 决定
→ 拆分 → Implement → Review 失败 → 修正
→ Review 通过 → Commit → 结果反馈 → 接受
```

另测：无项目、项目读取失败、无文件范围、路径失效、权限拒绝、重复提交、刷新恢复和窄屏布局。

### 12.4 质量门禁

每个里程碑必须通过：

```text
npm run lint
npx tsc -p tsconfig.app.json --noEmit
npm run build
npm run test
npm run test:e2e
```

并完成 1440px、1024px、768px 截图检查和键盘流程检查。

## 14. 计划批准门

批准开发前必须确认以下默认决策：

1. 使用 Tauri 2 作为本地运行壳层，React/Vite 作为全新 renderer 实现，不迁移原型代码。
2. `.agentup/` 是唯一项目事实来源，SQLite 只做索引和缓存。
3. 先实现本地可替换 Agent provider，再接入具体模型服务。
4. 先完成一条真实纵向链路，再扩展全部场景和高级治理。
5. 不迁移当前 `localStorage` demo 数据。

计划批准后的第一阶段只在仓库根目录做 M0，不修改 `properties/react`；M0 通过后才进入事实层开发。

## 15. 需要补充确认的产品边界

这些问题原规格没有完全定义，但不先决定会直接影响数据模型、权限和 UI：

### 15.1 使用者和身份

- 第一版是单机单用户，还是需要多个本地用户/团队成员。
- Agent 是否有稳定身份、角色和能力声明。
- 用户是否能看到其他用户的评论和决定。
- 是否需要登录、账号、团队、邀请和远程同步。

默认建议：第一版只做单机单用户；保留 `author_id`、`agent_id` 和 `source` 字段，不实现账号和远程协作。

### 15.2 项目边界

- 一个项目是否只能对应一个本地根目录。
- 是否支持 monorepo、多根目录、子模块、软链接和嵌套项目。
- 项目目录被移动、删除、改名或权限变化后如何处理。
- 是否允许同一个目录被多个 AgentUp 实例打开。
- 是否支持只读项目。

默认建议：第一版一个项目对应一个根目录；支持只读扫描和目录失效提示；禁止跨根目录写入。

### 15.3 运行环境

- 第一版支持哪些 macOS 版本，是否同时支持 Windows/Linux。
- 是否必须离线工作。
- 模型服务不可用时，哪些本地功能仍可用。
- 是否允许后台运行，应用关闭后 Agent 是否继续执行。

默认建议：第一版先支持 macOS 和 Windows；Linux 放到第二阶段；讨论、历史和事实读取离线可用；Agent 执行需要明确的在线状态；应用关闭后停止可取消运行。

## 16. 外部文件与并发变化

项目文件不是 AgentUp 独占资源，用户或其他工具可能同时修改它们。必须定义：

- 执行前读取的文件 hash 和 revision。
- 执行中发现文件变化时暂停并提示冲突。
- 写入前再次校验 hash，禁止静默覆盖用户修改。
- 外部删除、重命名和移动文件时如何更新范围。
- Git 分支、未提交变更和 worktree 的处理。
- 符号链接是否跟随，禁止链接逃逸项目根目录。
- 文件编码、二进制文件、超大文件和生成文件的处理。
- `.gitignore`、`.agentupignore` 和敏感文件排除规则。

完成标准：任何外部变化都不会静默丢失用户修改；冲突有可恢复状态、差异信息和下一步动作。

## 17. Agent 上下文工程规范

真实 Agent 的质量取决于上下文边界，必须单独制定：

- 系统指令、项目指令、需求、讨论、范围、工具输出的优先级。
- 当前事实和历史事实的有效期标记。
- 文件内容截断、摘要、token 预算和排序规则。
- 何时自动扩大范围，何时必须请求用户确认。
- Agent 输出的结构化格式、schema 校验和非法输出处理。
- 外部文档、项目文件和命令输出全部视为不可信数据，防止 prompt injection。
- 每次 Agent 回复记录模型、provider、prompt 版本、输入引用和输出版本。
- 是否允许 Agent 读取密钥文件、环境变量、网络资源和隐藏目录。
- 长任务上下文压缩后如何保留决定、约束和未解决问题。
- 如何重放一次 run 以复现结果。

完成标准：同一事实输入和同一 prompt 版本可以定位 Agent 使用了哪些上下文；非法或越权输出不会直接写入事实。

## 18. 工具、权限和执行安全

必须建立工具白名单，而不是只做一个“允许命令”开关：

- 文件读取、文件写入、目录创建、删除、网络访问、命令执行分别授权。
- 命令按项目、任务和工具类型授权，不能由 Agent 自行扩大权限。
- 高风险命令需要用户批准，批准范围、次数和有效期可见。
- 子进程超时、输出上限、内存上限和进程树清理。
- 命令环境变量和日志中的密钥脱敏。
- 禁止访问项目根目录外路径、系统密钥链和其他项目事实。
- 执行前提供将要修改的文件范围和预计副作用。
- 写入失败时保留原文件、临时文件和恢复指针。

完成标准：能够证明 Agent 不能绕过权限、不能写出范围、不能读取未授权数据；所有批准和拒绝均有事件记录。

## 19. 运行队列、取消和重试

原规格定义了暂停、连续失败和独立 Review，但还需要具体规则：

- 一个项目是否同时只允许一个写入 run。
- 多个只读分析是否可以并行。
- 同一任务重复点击开始是否幂等。
- 暂停发生在当前工具调用中时如何处理。
- 取消是否等待子进程退出，多久后强制终止。
- 自动重试的错误分类、次数、退避和成本上限。
- Review 失败和工具失败是否走不同路径。
- 连续失败按任务、需求还是项目统计。
- 应用崩溃或电脑休眠后 run 是恢复、失败还是需要用户重新开始。

完成标准：每个 run 都有唯一 ID、明确状态、取消结果、重试原因和最终出口；重复操作不会创建重复写入。

## 20. 事实一致性、迁移和恢复

除了基本 writer，还必须定义：

- schema 版本和向后兼容窗口。
- 应用升级时如何迁移 `.agentup/`。
- 应用版本和事实版本不兼容时如何只读打开。
- manifest 损坏、单个事实文件损坏和部分写入时的恢复策略。
- 事件重复、乱序、丢失和重复消费的处理。
- 附件缺失、孤立附件和重复附件的清理策略。
- SQLite 索引重建进度和失败恢复。
- 备份格式版本、校验和、恢复演练。
- 用户主动导出、导入和删除数据的范围。

完成标准：模拟进程中断、磁盘满、文件损坏、版本升级和索引删除后，事实仍可诊断、恢复或明确进入人工处理状态。

## 21. 搜索、过滤和通知

这些不是首屏核心，但真实使用很快会需要：

- 跨项目搜索需求、讨论、文件路径、结果和事件。
- 按状态、项目、负责人、更新时间和风险过滤。
- 搜索是否读取 SQLite 索引，结果如何回到事实文件。
- 新决定、Review 失败、运行失败和结果待验收是否需要通知。
- 通知是否只在 App 内，是否允许系统通知。
- 用户关闭通知后，如何保证待处理事项仍可见。

默认建议：第一版做 App 内搜索和待处理计数；不做邮件、移动端和远程通知。

## 22. 可访问性、国际化和内容规范

- 所有主要流程可仅用键盘完成。
- 对话框打开、关闭、错误和焦点回归可测试。
- 状态不能只依赖颜色；图标、文字和语义标签一致。
- 中文长文本、英文路径、代码块和超长文件名不破坏布局。
- 日期、时间、数字和路径使用 locale-aware formatter。
- 用户输入、Agent 输出和外部文件内容要区分来源。
- 错误消息必须说明原因和下一步。
- 需要决定是否支持英文、深色模式、系统缩放和高对比度模式。

完成标准：axe/键盘检查无 P0/P1 阻塞；1440、1024、768 和系统缩放下无横向溢出。

## 23. 性能和资源预算

必须提前设定上限：

- 最大项目文件数、单文件大小、单任务评论数和附件大小。
- 首次扫描、增量扫描和 SQLite 重建的目标时间。
- 讨论流和历史列表超过 50 条后的虚拟化或分页策略。
- 大文件不得一次性读入 renderer。
- Agent 上下文 token、单任务最大 run 时长和单任务成本。
- 并发 Agent 数和本地 CPU、内存、磁盘预算。
- UI 首屏加载和交互响应目标。

完成标准：超过上限时显示明确限制或进入降级路径，不能卡死、崩溃或静默丢数据。

## 24. 可观测性和诊断

- 结构化本地日志，区分 UI、事实层、Tauri command、Agent、工具和索引错误。
- 每个请求、run、事件和 Tauri command 使用 correlation ID。
- 用户可以导出脱敏诊断包。
- 日志保留周期、大小上限和清理策略。
- 不默认上传需求、项目内容、评论、附件和命令输出。
- 记录性能指标、失败率、重试次数和上下文大小。
- 为不可复现问题提供 run replay 或最小复现 fixture。

完成标准：用户报告一个失败 ID 后，开发者能定位到事实 revision、Agent run、工具调用和错误出口。

## 25. 发布、升级和支持

- Tauri 打包、代码签名和更新策略。
- 开发版、测试版和稳定版的事实目录兼容规则。
- 升级失败时的回滚和事实备份。
- 安装、卸载和应用数据清理的区别。
- 版本发布说明、已知问题和故障排查文档。
- 数据删除和隐私说明。
- 是否允许用户导出全部事实用于迁移或审计。

默认建议：第一版提供手动导出、手动更新和本地诊断包，不做静默自动更新。

## 26. 新增里程碑门禁

在原有 M0-M7 之外，加入以下强制门：

### M0-A：产品边界门

必须批准：单用户/多人、运行环境、离线策略、项目边界、应用关闭后的 run 行为。

### M0-B：事实和安全门

必须批准：schema、事件、revision、范围、附件、工具权限、路径规则、备份和恢复策略。

### M0-C：Agent 质量门

必须批准：上下文优先级、prompt 版本、结构化输出、成本上限、重试、重放和 prompt injection 防护。

### M2.5：外部变化门

必须通过：外部文件变化、Git 未提交变更、软链接、冲突写入、目录失效和恢复测试。

### M5.5：运行可靠性门

必须通过：幂等启动、取消、超时、重试、休眠恢复、崩溃恢复和子进程清理。

### M7.5：发布门

必须通过：打包安装、升级、事实迁移、备份恢复、诊断包、隐私检查和安全测试。

## 27. 明确的首版开发边界

为了防止计划变成无限制平台建设，首版暂定只做：

- 单机单用户。
- macOS 和 Windows 本地运行；Linux 在第二阶段接入。
- 项目内 `.agentup/`。
- 一个项目一个根目录。
- App 内讨论和通知。
- 一个主 Agent、一个执行 Agent、一个独立 Review Agent。
- 文件读取、范围计算、受限文件写入和受限命令执行。
- 三个完整场景。
- 手动导出和恢复检查。

首版明确不做：

- 账号、团队、远程同步和多人实时协作。
- 移动端、邮件、系统级推送。
- 多根目录和跨项目写入。
- 云端任务队列和应用关闭后继续运行。
- 自动更新、插件市场和第三方扩展系统。
- 全量历史自动导入。
- 从 `properties/react` 自动迁移组件、样式、数据或用户状态。

## 28. 最终开发启动条件

只有以下内容全部批准，才开始 M0 实施：

1. 本计划中所有“默认建议”被接受或被改写。
2. Tauri 2 运行壳层被接受，平台 WebView 差异和 Rust runtime 维护成本被接受。
3. 首版开发边界被接受。
4. 事实 schema、状态机、事件清单和 Tauri command/event 清单形成初稿。
5. 工具权限、路径安全、备份和恢复策略形成初稿。
6. 三个场景的验收脚本形成初稿。

批准后仍不会直接接入真实模型。先在仓库根目录完成 M0 的合同和风险验证，再进入事实层；事实层通过恢复测试后，才接入 Agent runner。
