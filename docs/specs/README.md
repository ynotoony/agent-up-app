# 需求与规格（specs）

## 架构

- 本目录保存**当前确认的需求真相**：一份规格 = 一条已确认的需求，可变——改需求直接改规格，并追加一行到 `../changes.md`。
- 规格只写"当前是什么"，不保存历史；历史在 `../changes.md`（语义变更）、`../adr/`（决策理由）和 Git 历史里。
- 领域词汇用 [`../CONTEXT.md`](../CONTEXT.md) 的统一语言，不自造近义词。

## 目录清单

| 名字 | 地位 | 功能 |
| --- | --- | --- |
| `README.md` | 层索引 | 写作规则、状态机与规格模板。 |
| `<NN>-<slug>.md` | 规格 | 一条已确认需求；新建时复制下方模板。 |

## 状态机

`draft → confirmed → superseded`。被取代的规格在文件头标注取代者编号，不删除。

## 写作规则（两条硬规则）

1. **不写具体文件路径和代码片段**——它们过期最快。例外：原型产出的片段若比散文更精确（状态机、schema、类型形状），可内联并注明来自原型，只保留决策密集部分。
2. **测试决策先划接缝（seam）**：优先复用既有接缝，用最高接缝，接缝越少越好（理想是一个）；只测外部行为，不测实现细节。

## 规格模板

```markdown
# SPEC-<NN> — <标题>

## 问题陈述
用户遇到的问题，从用户视角写。

## 方案
从用户视角描述解决方案。

## 用户故事
详尽的编号清单：`作为<角色>，我要<功能>，以便<收益>`。覆盖功能的所有方面。

## 实现决策
- 将新建/修改的模块及其接口
- 技术澄清、架构决策、schema 变更、API 契约、具体交互
- 不写具体文件路径和代码片段（见写作规则例外）

## 测试决策
- 好测试的标准：只测外部行为，不测实现细节
- 测试哪些模块；仓库内的先例测试

## 范围外
本规格明确不做的事。

## 附注
其他说明。
```
